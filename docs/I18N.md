# Languages (Arabic, French, English)

The app speaks English, French and Modern Standard Arabic (right to left). See Phase 12 in [ADMIN_ROADMAP.md](ADMIN_ROADMAP.md).

## How the language is chosen

1. A saved choice: the `wgv_locale` cookie, and the member's profile (`UserProfile.locale`) once signed in.
2. Otherwise the browser's languages (`Accept-Language`), falling back to **French**.

The server reads it in the root layout (`app/layout.tsx`), so the first paint already has the right `lang`, `dir` and font. When a member signs in, the language saved on their profile wins (it follows them across devices); changing it in the sidebar, Settings or on the sign-in pages saves it to both.

## Frontend: adding text

Messages live in `frontend/src/i18n/messages/{en,fr,ar}/<area>.ts`. English is the source; French and Arabic are typed against it, so **a missing key fails the type check**.

```tsx
const t = useT();
t('events.title');
t('events.going', { count: 3 });          // plurals pick the right form
t('feed.post.postedIn', { space: name }); // {name} placeholders
```

- **Plurals** are objects with `one` / `other` (Arabic also uses `zero`, `two`, `few`, `many`). Don't name an ordinary key `other`: an object with an `other` key is treated as a plural.
- In components that can render on the server, use `<T k="common.loading" />`.
- Outside React (helpers), use `translate(messages[activeLocale()], messages.en, activeLocale(), key)`.
- Dates and numbers: pass `activeIntl()` to `toLocaleDateString` etc. Arabic keeps Western digits (`ar-u-nu-latn`).
- A new area file: add it to `en/`, `fr/` and `ar/`, then list it in `messages/index.ts`.

## Right to left

Use logical Tailwind classes: `ms-`/`me-`, `ps-`/`pe-`, `start-`/`end-`, `text-start`/`text-end`, `border-s`/`border-e` (not `ml-`, `left-`, `text-left`…). Arrows that point "back" or "next" get `rtl:rotate-180`. Fields where people type Latin text (email, username, password, links) can use `dir="ltr"`.

## Backend messages

Services keep throwing plain English errors. `middleware/locale.middleware.ts` reads `Accept-Language` (the app sends it on every request) and translates the `error` of every response with `lib/i18n.ts`: exact messages in `MESSAGES`, messages with numbers or names in `PATTERNS`. Anything missing stays in English, so add new user-facing errors there.

## Team-written content

Spaces, badges, levels, guide sections, quiz questions and help articles keep their main (English) text in their usual fields and the other languages in a `translations` column: `{ fr: { name: '…' }, ar: { … } }`.

- **Reading**: the same middleware puts every object with a `translations` field in the reader's language on the way out (`lib/localize.ts`) and drops the field, so services just select `translations: true` next to the text. An empty or missing translation falls back to the main text, entry by entry for lists (quiz options). Text built inside a service (an error naming a space, a lock reason naming a level) uses `localizeRecord(record)`.
- **Editing**: `/api/admin/*` and `/api/help/manage` return content as stored, with every language; the help editor loads an article with `?raw=1`. Editors use `components/LanguageTabs` with the helpers in `lib/translations.ts` (`bindField`, `isTranslated`, `cleanTranslations`); a dot marks a language with missing text.
- **Starter content**: French and Arabic versions of the starter spaces, badges, levels (`backend/prisma/content-translations.ts`) and help articles (`help-articles.fr.ts`, `help-articles.ar.ts`). `yarn translations:seed` adds them to records with no translations whose English is unchanged; `yarn help:seed` creates new articles with them.
